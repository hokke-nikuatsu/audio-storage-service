# Implementation Plan

大きなタスク（1〜10）を、それぞれ1つのブランチと1つの PR にする。小さなタスク（1.1 など）は、`/kiro-impl` が1つずつ実装してコミットする単位。

- [x] 1. Gradle の骨組みと、ビルドで行うチェック
- [x] 1.1 5つのモジュールと共通のビルドの設定を作る
  - `domain`、`application`、`adapter`、`web`、`bootstrap` の5つのモジュールと、共通の設定をまとめる `build-logic` を作る
  - 共通の設定に、Kotlin 2.3 系、Java 25 の toolchain、コンパイラの警告をエラーにする設定、ktlint、detekt 2.0、Kotest を入れる。ライブラリとプラグインのバージョンは1か所にまとめる
  - JDK を手元に入れずに Gradle に取ってこさせるため、toolchain の取得の設定（foojay の resolver）を入れる。detekt の設定は、既定との差分だけを書く
  - 後のタスクで並行して同じファイルを書き換えないよう、すべてのライブラリとプラグインのバージョンと、`adapter` の依存をここで宣言しておく。`adapter` の本体の依存は jOOQ と SLF4J だけにし、sqlite-jdbc と Flyway はコード生成の設定とテストの依存にだけ入れる（design.md の Allowed Dependencies）
  - `bootstrap` には Spring Boot 本体と Kotest の Spring の拡張だけを入れる。DB を使う starter（jOOQ、Flyway）と sqlite-jdbc は、接続先の設定と一緒に 8.2 で入れる。`bootstrap` の依存を書き換えるのは 8 だけなので、並行するタスクとは衝突しない
  - `bootstrap` に Spring Boot の起動のクラスを置き、Spring のコンテキストが起動するだけのテストを1本書く。これで、Kotest と detekt 2.0 が Kotlin 2.3 と Spring Boot 4.1 で動くかを確かめる。動かなければ ADR-0009、ADR-0020 の見直し条件に従い、人に判断を仰ぐ
  - 完了の状態: `./gradlew build` が、5つのモジュールすべてで ktlint・detekt・テストを走らせ、Spring のコンテキストが起動するテストを含めて成功する
  - _Requirements: 4.1_
- [x] 1.2 モジュールの依存の向きを、ビルドで強制する
  - 依存してよいモジュールの表を `build-logic` に1か所だけ書き、表にない依存（テストの依存を含む）を宣言したらビルドを失敗させる
  - 依存は `implementation` で宣言し、`api` は `application` から `domain` への依存だけに使う
  - 完了の状態: 表にない依存（たとえば `application` から `adapter`）を足すとビルドが失敗し、表のとおりなら成功する
  - _Requirements: 4.1_
- [x] 1.3 プッシュの前と CI のチェックに、Gradle のチェックを加える
  - lefthook のプッシュの前のチェックに、Gradle の ktlint・detekt・テストを加え、チェックの規約に書き足す
  - CI のジョブで、Gradle のキャッシュ（`gradle/actions/setup-gradle` など）と ffmpeg を用意し、同じチェックを走らせる。JDK の取得と依存の取得が入るので、ジョブのタイムアウトを見直す
  - 完了の状態: `lefthook run pre-push` が Gradle のチェックを含んで成功し、PR の CI でも同じチェックが走って成功する
  - _Requirements: 4.1_

- [ ] 2. ID・パス・フォーマットの値と、ID の確認
- [x] 2.1 値、ポート、結果の型を定義する
  - ユーザー ID とフレーズ ID の値に、先頭が 0 ではない数字だけの並びで `Long` に収まるものだけを受け付ける読み取りを持たせる
  - ユーザー ID とフレーズ ID の組、保存先のルートからの相対パス、送受信用のフォーマット（m4a だけ）の値を作る
  - DB、ディスク、変換の3つのポートと、保存と取得の結果の型、エラーの種類を design.md のとおりに定義する
  - 完了の状態: `domain` と `application` がビルドでき、ポートと結果の型が design.md の Components and Interfaces と一致する
  - _Requirements: 2.3, 3.2, 3.3_
- [ ] 2.2 ID の確認と、ポートのフェイクを作る
  - 生の ID を受け取り、形式と登録の両方を確かめて、組か「ユーザーが見つからない」「フレーズが見つからない」を返す。ユーザー ID を先に確かめる
  - DB、ディスク、変換のポートのフェイクを、テストのコードに手で書く。失敗させる振る舞いを、クラスの名前と中身から読めるようにする。並行して進める 3 と 4 でフェイクを書き換えずに済むよう、変換の Rejected・TooLarge・例外、DB の切り替えの例外、録音のパスがない場合を、ここですべて再現できるようにする
  - 完了の状態: 単体テストで、`abc`、`0`、`Long` を超える数、登録されていない ID がいずれも見つからない扱いになり、ユーザーとフレーズの両方が不正なときはユーザーが見つからないになることが確かめられる
  - _Requirements: 3.1, 3.2, 3.3_

- [ ] 3. (P) 保存の手順を作る
  - ID を確かめ、新しいファイルのパスを割り当て、m4a を WAV に変換してそこに書き、DB のパスを切り替え、古いファイルを消す
  - m4a ではない、または変換後の WAV が上限を超えたときは、新しいファイルを消して拒む。変換や DB の切り替えで失敗したときは、新しいファイルを消して例外を上げ直す
  - 完了の状態: 単体テストで、新規と置き換えで結果が分かれること、置き換えで古いファイルが消えること、拒んだときと失敗したときに DB のパスが変わらず新しいファイルが残らないこと、ID が見つからないときに変換と保存のポートが呼ばれないことが確かめられる
  - _Boundary: SaveRecordingUseCase_
  - _Depends: 2.2_
  - _Requirements: 1.1, 1.3, 1.5, 1.6, 1.7, 3.1_

- [ ] 4. (P) 取得の手順を作る
  - ID を確かめ、フォーマットを確かめ、組の録音のパスを読み、WAV を m4a に変換して返す
  - 完了の状態: 単体テストで、録音を m4a で返すこと、録音がない・フォーマットが m4a ではないときに拒むこと、変換に失敗したときに例外が上がること、ID が見つからないときに変換のポートが呼ばれないことが確かめられる
  - _Boundary: GetRecordingUseCase_
  - _Depends: 2.2_
  - _Requirements: 2.1, 2.2, 2.3, 2.4, 3.1_

- [ ] 5. DB のアダプタ
- [ ] 5.1 (P) スキーマと初期データのマイグレーションと、jOOQ のコード生成を用意する
  - 3つのテーブル（有効なユーザー ID、有効なフレーズ ID、組と保存したファイルのパスの対応）を作るマイグレーションと、ID 1〜3 を入れる初期データのマイグレーションを書く
  - ビルドの中で、スキーマのマイグレーションだけを流した一時的な SQLite を作り、そこから jOOQ のコードを生成する
  - アーキテクチャの現状の文書（`docs/architecture.md`）を作り、ER 図を書く
  - 完了の状態: `./gradlew build` で jOOQ のコードが生成され、生成のための SQLite には初期データが入っていない
  - _Boundary: JooqRecordingRepository_
  - _Requirements: 4.2, 5.4_
- [ ] 5.2 DB のポートを jOOQ で実装する
  - ID の存在の確認、組のパスの読み出し、古いパスの読み出しと upsert を1つのトランザクションで行うパスの切り替えを実装する
  - 完了の状態: 一時的な SQLite にスキーマと初期データのマイグレーションを流した結合テストで、切り替えが古いパスを返して組ごとに1行を保つこと、初期データの ID 1〜3 が存在し、それ以外は存在しないと答えることが確かめられる
  - _Requirements: 1.1, 1.3, 1.7, 4.2, 5.4_

- [ ] 6. (P) ディスクのポートを実装する
  - 設定のルートの下に、組のディレクトリと UUID のファイル名のパスを割り当てる。パスは型付きの ID と UUID だけから作る
  - ファイルの削除は、ファイルがなくても消せなくても例外を上げず、消せなければ警告のログを残す
  - 完了の状態: 一時ディレクトリを使った結合テストで、割り当てが毎回違うパスを返し、そのディレクトリができること、ないファイルの削除が失敗しないことが確かめられる
  - _Boundary: LocalRecordingStorage_
  - _Depends: 2.1_
  - _Requirements: 5.3_

- [ ] 7. 変換のアダプタ
- [ ] 7.1 (P) テスト用の音声を用意する
  - 受け付ける m4a として、iPhone のボイスメモで既定の圧縮のまま録った数秒の録音を、人に用意してもらってテスト用の置き場所に置く
  - 受け付けないファイル（テキストを m4a と名付けたもの、WAV、MP3、ALAC の m4a、途中で切れた m4a）を ffmpeg で作るスクリプトを書き、作ったファイルを置く
  - 完了の状態: スクリプトを流すと受け付けないファイルがすべてでき、受け付ける m4a を ffprobe が MP4 と AAC と読む
  - _Boundary: FfmpegAudioConverter_
  - _Requirements: 1.5_
- [ ] 7.2 変換のポートを ffmpeg と ffprobe で実装する
  - 入力を一時ファイルに書き、入力の形式を `-f mov` に固定した ffprobe で、最初の音声のストリームが AAC であることを確かめる
  - WAV への変換では、サンプリングレートとチャンネル数を保ち、出力の大きさに上限を付けて、上限に達したら上限超過として返す。m4a への変換は結果をバイト列で返す
  - 1回の起動に 30 秒のタイムアウトを設け、失敗とタイムアウトは変換の失敗の例外にする。一時ファイルは変換の中で消す
  - 完了の状態: 結合テストで、受け付ける m4a がサンプリングレートとチャンネル数を保った WAV になり、戻した m4a を ffprobe が AAC と読み、受け付けないファイルをすべて拒み、上限を小さく設定すると上限超過になることが確かめられる
  - _Requirements: 1.1, 1.5, 1.6, 2.1_

- [ ] 8. HTTP の入口と起動の組み立て
- [ ] 8.1 HTTP の入口とエラーの応答を作る
  - 保存と取得の2つのエンドポイントで、`audio_file` のフィールドを受け取り、ユースケースの結果を 201・204・200 とエラーのステータスにする
  - 空のファイルは、パートがないときと同じ例外にしてエラーの応答に任せる
  - エラーの種類と Spring の例外（パートがない、multipart ではない、大きすぎる）、想定外の例外を、`code` を持つエラーの JSON にする場所を1つにする
  - 完了の状態: `web` がビルドでき、エラーの表のすべての行に、対応するステータスと `code` の変換がある
  - _Requirements: 1.2, 1.4, 1.5, 1.6, 1.7, 2.2, 2.3, 2.4, 3.2, 3.3, 5.2_
- [ ] 8.2 起動と組み立て、設定を作る
  - Spring Boot の起動、設定値の読み込み、3つのアダプタを設定値と jOOQ を渡して作る組み立てを書く
  - `bootstrap` に、DB を使う starter（jOOQ、Flyway）と sqlite-jdbc を入れる
  - 設定に、外部キーを有効にした SQLite の接続（接続は1本）、マイグレーションと初期データの場所、ファイルの上限 10MB と Tomcat の読み捨ての上限、保存先のルート、ffmpeg と ffprobe のパス、タイムアウト、WAV の上限を書く
  - 完了の状態: 一時的な DB と保存先で Spring Boot を起動するテストで、サービスが起動し、DB に初期データの ID が入った状態になることが確かめられる
  - _Requirements: 4.1, 4.2_

- [ ] 9. HTTP を通した全体のテストと、アーキテクチャの図
  - Spring Boot を一時的な DB と保存先で起動し、課題の `curl` と同じ要求を送る
  - 保存して取得できる、置き換えで 204 になる、初期データの ID で受け付ける、空のファイルが 400 になる、404・413・415 の代表を1つずつ確かめる
  - アーキテクチャの現状の文書に、保存と取得のシーケンス図と、検証とエラーの分岐のフロー図を書く
  - 完了の状態: 全体のテストがすべて成功する
  - _Requirements: 1.1, 1.2, 1.3, 1.4, 1.5, 1.6, 2.1, 2.3, 3.2, 4.2, 5.2_

- [ ] 10. Docker で起動できるようにする
  - Dockerfile の中でマルチステージでビルドする。ビルドの段は JDK 25 のイメージで、テストを流さずに jar を作るタスクだけを流す（jOOQ のコード生成は含む。テストは ffmpeg がないと失敗させる決まりのため）。実行の段は ffmpeg を入れた JRE のイメージにして、root ではないユーザーで 8080 番で待ち受ける。`/data` をボリュームにする
  - ホストの 80 番をコンテナの 8080 番に割り当てる1サービスの compose の設定を書く
  - README に、起動方法、`curl` の例、手を抜いた箇所と本番運用ならどうするかを書く
  - 完了の状態: `docker compose up --build` で起動し、課題の `curl` の手順で、初期データの ID で保存と取得ができる（手で確かめる）
  - _Depends: 9_
  - _Requirements: 4.1, 4.2, 5.1_
