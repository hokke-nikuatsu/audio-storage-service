# 開発の進め方の規約

開発の進め方（ドキュメントの置き場、開発の流れ、要件 ID、ブランチ、コミット、PR）の規約。レビューの規約は [review.md](review.md) に、チェックの規約は [checks.md](checks.md) にある。判断の理由は [docs/adr/](../adr/README.md) にある。

## ドキュメントの置き場

ドキュメントの一覧と役割は、この表だけに書く。ほかのドキュメントはこの表を参照する。

| 種類 | 置き場 | 書くこと | 読むタイミング |
|---|---|---|---|
| 作業の進め方の規約 | [docs/conventions/](.) | ドキュメントの置き場、開発の流れ、要件 ID、ブランチ、コミット、PR、レビュー、チェック | すべての作業の前 |
| コードに関する規約 | `.kiro/steering/` | 技術スタック、アーキテクチャ、コーディング規約 | コードを読み書きする作業の前 |
| 仕様 | `.kiro/specs/<feature>/` | 要件（requirements.md）、設計（design.md）、タスク（tasks.md） | その機能の spec や実装の作業の前 |
| 判断の理由 | [docs/adr/](../adr/README.md) | 1つの判断につき1ファイル | 判断の理由を確かめるとき |
| AI の入口 | [AGENTS.md](../../AGENTS.md)、[CLAUDE.md](../../CLAUDE.md) | 言語、この規約の取り込み、Claude Code 固有の設定 | — |
| 人の入口 | [README.md](../../README.md) | 概要、起動方法、この表へのリンク | — |

- 同じことを2か所に書かない
- ADR の書き方と運用は [docs/adr/README.md](../adr/README.md) にある
- コードに経緯を書かない。経緯は ADR と PR に残す
- ドキュメントの種類を追加したら、この表に行を足す

## 開発の流れ

cc-sdd による仕様駆動で進める。要件・設計・タスクは、人が内容を確認して承認してから次へ進む。承認したら、`.kiro/specs/<feature>/spec.json` の `approvals.<段階>.approved` を `true` にして記録する（人が書き換えるか、人の指示で AI が書き換える）。人の確認を経ずに承認済みにする `-y` は使わない。

1. 要件: `/kiro-spec-init` → `/kiro-spec-requirements` → 人が requirements.md を承認する
2. 設計: 技術選定を1つずつ決めて `/adr` で記録し、steering に反映する → `/kiro-spec-design` → 人が design.md を承認する
3. タスク: `/kiro-spec-tasks` → 人が tasks.md を承認する（1タスクが1つの PR に収まる粒度か、依存関係に沿った順番か、すべての要件がどれかのタスクに入っているか）
4. 実装: タスクごとにブランチを切り、`/kiro-impl <feature> <タスク番号>` で1タスクずつ実装して PR を出す

人が承認する spec は requirements.md、design.md、tasks.md の3つで、spec.json と research.md はレビューの対象にしない。

## 要件 ID

- cc-sdd の文書の中では、数字の ID（`1.2`）をそのまま使う
- cc-sdd の文書の外（テスト名、PR、ADR、コミット）では `REQ-1.2` と書き、requirements.md の `1.2` を指す

## ブランチ

- 名前は `{prefix}/{内容を表す英語のケバブケース}` とし、40文字以内にする（例: `feature/upload-audio`）
- main から切る。main には PR を経由してだけ入れる

| prefix | 用途 |
|---|---|
| `feature` | 機能の開発 |
| `bugfix` | 不具合の修正 |
| `test` | テストだけの変更 |
| `docs` | ドキュメントだけの変更 |
| `chore` | 設定、ツール、依存関係などの変更 |

## コミット

- メッセージの1行目は `{prefix}: {要約}` とし、要約は「〜する」と動詞で言い切る。1行空けて、本文に何をなぜ変えたかを書く
- 1つのコミットには1つの関心ごとだけを入れ、1行目で含まれる変更をすべて説明できなければ分ける
- AI が書いたコミットは、本文の末尾に AI を `Co-Authored-By:` で書く
- 著者は、このリポジトリの git の設定（`git config --local`）にある個人のアカウントにする
- コミットは `/commit` で作る。`/kiro-impl` は実装のタスクごとに自分でコミットを作るが、メッセージはこの節に従う

| prefix | 用途 |
|---|---|
| `add` | ファイルや機能を新しく足す |
| `fix` | 不具合や誤りを、意図した状態に直す |
| `change` | 既存の振る舞いや規約の意図を変える |
| `refactor` | 振る舞いを変えずに、構造や書き方を直す |
| `docs` | ドキュメントだけを変える。新しく足すときも含む。skill と PR テンプレートは AI やツールの動きを変えるので含まない |

## PR

- 1つの PR には1つの関心ごとだけを入れる。差分は1,000行未満、実装の PR は300行程度を目安にする
- タイトルは日本語で書き、「〜する」と動詞で言い切る
- PR を出す前に `/review` でレビューする。流れは [review.md](review.md) にある
- PR は `/pr` で作り、本文は [PR テンプレート](../../.github/pull_request_template.md) の見出しに沿って書く
- assignee に作成者を入れる
- コミットを追加したら、`/pr update` で本文を差分と突き合わせて書き直す
- マージは人が行う
