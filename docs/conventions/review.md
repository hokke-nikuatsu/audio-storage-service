# レビューの規約

PR の AI レビューと、人の判断の規約。判断の理由は [ADR-0001](../adr/0001-spec-driven-ai-development-with-human-judgment.md) にある。

## 流れ

1. PR を出す前に `/review` を実行する。レビューは、会話の履歴を持たない別のセッションで行われる。結果は `.review/<ブランチ名>.md`（`/` は `-` に置き換える）に書き出され、`/review` を実行した会話に報告される
2. `/pr` が結果を PR 本文の「AI レビュー結果」に入れる
3. 人が指摘ごとに対応を決め、「人の判断」に書く。判断は人が決める。書き込むのは人でも、人の指示を受けた AI でもよい
4. 人の判断を書いてから、人がマージする。自分の PR は GitHub で approve できないため、これを approve とみなす

AI は approve もマージもしない。

## 観点

観点ごとに、何と比べて、どんな性質の問題を見るかを決める。例は見つけるための手がかりで、例にない問題でも同じ性質なら指摘する。

| 観点 | 比べるもの | 見る問題の性質 | 例 |
|---|---|---|---|
| 仕様との一致 | 要件、タスク、PR の目的 | 作ったものが、求められたものとずれている | 要件の過不足、目的と関係ない変更、要件 ID とひもづかないテスト |
| シンプルさ | 要件を満たす最小の実装、情報ごとの正の置き場（SSOT） | 要件が求める以上に複雑な作り方をしている。同じ情報を、正の置き場を参照せずに複数の場所に持っている | 使い道が1つしかない抽象化、要件にない設定や拡張ポイント、起こりえない状況への防御、不要な依存、本番を見越した作り込み、同じ規約・定義・定数・コメントの複製 |
| 正しさ | 実際に起こりうる入力と状態 | ある入力や状態のときに、期待と違う結果になる | 境界値、見落としやすい分岐、例外の握りつぶし、部分的な失敗（ファイルと DB の片方だけ成功など）、資源の閉じ忘れ |
| セキュリティ | 外から来る入力と、外へ出る情報 | 悪意のある入力で、意図しない操作や情報の漏れが起きる | 入力の検証不足（拡張子だけを見るなど）、パスの組み立て、外部プロセスへの引数の渡し方、サイズの上限、エラー応答やログでの情報漏れ |
| 設計と境界 | design.md、ADR、steering | 決めた構造や依存の向きから外れている | 層をまたぐ呼び出し、決めたインターフェースを通らない利用、責務の混在 |
| テスト | 変えた振る舞い | 振る舞いが壊れても、テストで気づけない | 変えた振る舞いにテストがない、アサーションが結果を確かめていない。カバレッジの数字は見ない |
| 読みやすさ | steering の規約 | 読む人が誤解する、または規約に反している | 規約違反、実際の動きと食い違う命名やコメント |

## 指摘の書き方

- 規約に照らす指摘は、根拠を規約（`docs/conventions/`）、steering、ADR、spec の記述に限る。一般論の良し悪しを持ち込まない
- バグの指摘は、どの入力や状態でどう壊れるかを書く
- 確信が持てないものは出さない。好みの指摘はしない
- 指摘には優先度、場所（ファイルと行）、根拠、修正案を付ける

## 指摘の数

指摘の数に、目安も下限も上限もない。見つかった問題はすべて書き、見つからなければ0件とする。AI のレビューは、問題の有無にかかわらず数件の指摘を出す形にそろいやすいため、次を守る。

- 0件は正しい結果として扱う。何か出さなければと考えて、根拠の弱い指摘や好みの指摘で数を埋めない
- 見つかった問題が多くても、数を理由に削らない
- 1つの指摘には1つの問題だけを書く。数を減らすために別々の問題をまとめたり、数を増やすために1つの問題を分けたりしない
- 出すか迷ったら、「どの入力でどう壊れるか」または「どの規約・ADR・spec のどこに反するか」を言えるかで決める。言えなければ出さない

## 優先度

| 優先度 | 定義 | マージ前の扱い |
|---|---|---|
| Critical | 取り返しがつかない。シークレットの混入、データの破壊 | 必ず直す |
| High | 外から見える振る舞いや契約を壊す。設計の境界に正面から反する | 必ず直す |
| Medium | リポジトリの中で閉じる問題。設計との整合、誤解を招く命名 | 人が判断する |
| Low | 直すと良くなるが、今のままでも問題が起きない | 人が判断する |

迷ったら低いほうを選ぶ。

## 指摘しない範囲

機械的なチェックで確かめているものと、人が手を入れていない生成物は指摘しない。同じルールを2か所で持つと、片方が古くなるため。チェックを追加したら、この表に行を足す。

| 指摘しないもの | 確かめている仕組み |
|---|---|
| cc-sdd が生成したファイル（`.gitattributes` で `linguist-generated` のもの） | 生成物で、人が手を入れていない |
| GitHub Actions のワークフローの書き方 | actionlint（`lefthook.yml` の `pre-push`） |
| ADR と design.md の行数 | doc-line-count（`lefthook.yml` の `pre-push`） |
| コミットの著者とコミッターのメールアドレス | commit-author（`lefthook.yml` の `pre-push`） |
| コミットメッセージの1行目の書式と、その後の空行 | commit-message（`lefthook.yml` の `pre-push`） |
| ブランチ名の書式と長さ | branch-name（`lefthook.yml` の `pre-push`） |
| シークレットの混入 | gitleaks（`lefthook.yml` の `pre-push`） |
| シェルスクリプトの書き方 | shellcheck（`lefthook.yml` の `pre-push`） |
| ADR の一覧の表が各 ADR から作ったものと同じか、ADR どうしの amends と amended by の対応、`lefthook.yml` のジョブとこの表の対応 | doc-consistency（`lefthook.yml` の `pre-push`） |
| ドキュメントの中のリンク切れとアンカー切れ | doc-links（`lefthook.yml` の `pre-push`） |
