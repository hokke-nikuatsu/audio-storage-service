# ADR-0005: チェックは手元のフックと CI で同じコマンドを走らせ、CI の結果を1つのジョブにまとめる

## 背景と課題

このリポジトリでは、AI がコードとドキュメントを書く。ブランチ名、ドキュメントの行数、シークレットの混入のように機械で確かめられる規約を、AI のレビューや人が毎回確かめると漏れが出る。機械で確かめられる規約を、どこで、どのように確かめるかを決める必要がある。

## 検討した選択肢

### CI だけでチェックする

- 良い点: 実行環境が1つで、手元にツールを入れなくてよい。チェックを飛ばせない
- 悪い点: プッシュして CI が終わるまで違反に気づけない。AI が直してはプッシュする往復が増える

### 手元のフック（lefthook）だけでチェックする

- 良い点: プッシュする前に違反に気づける
- 悪い点: `--no-verify` やフックを入れていない環境で飛ばせるので、main を守れない

### 手元のフックと CI で同じコマンドを走らせる

- 良い点: プッシュする前に気づけ、手元で飛ばしても CI で止まる。コマンドが1か所にあるので、手元と CI で結果が食い違わない
- 悪い点: 手元と CI の両方にツールを入れ、バージョンをそろえる仕組みが要る

## 決定

「手元のフックと CI で同じコマンドを走らせる」を選ぶ。違反に早く気づけることと、飛ばせないことを両立できるため。

- チェックのコマンドは lefthook の設定にだけ書き、CI は `lefthook run` でそれを呼ぶ。手元で確かめられないチェックだけを CI のジョブにする
- ツールのバージョンは mise で固定し、手元と CI で同じものを使う。mise で管理するのはチェック用のコマンドラインツールだけにし、JDK はビルド環境の判断で決める
- 既存のツール（actionlint、gitleaks、shellcheck、lychee など）があればそれを使う。独自のルールは `scripts/checks/` に置き、簡単なものはシェルで、ドキュメントの検査は Python の標準ライブラリだけで書いて、依存を増やさない
- CI の結果は `ci-status` ジョブにまとめ、main のルールセットはそれだけを必須にする。CI にジョブを足しても、ルールセットを変えずに済む
- CI は PR でだけ走らせ、ルールセットで最新の main を取り込んだ状態で `ci-status` が通ることをマージの条件にする。それぞれ CI を通った PR どうしの組み合わせで main が壊れることを、マージの前に防ぐため。main へのプッシュで走る CI は、落ちてもマージを取り消せないので置かない
- 失敗したときのメッセージには根拠のドキュメントを示し、AI と人が規約にたどり着けるようにする

## 影響

- 良い点: 機械で確かめられる規約はチェックが止めるので、AI のレビューと人は機械で確かめられないことに集中できる
- 受け入れたトレードオフ: 開発を始めるときに mise と lefthook の準備が要る。プッシュのたびにチェックの時間がかかる
- 本番運用なら: mise で固定したツールと GitHub Actions のバージョンを、Renovate で定期的に更新する

## 見直し条件

- プッシュする前のチェックに30秒以上かかるようになったら、遅いチェックを CI だけのジョブに移す
- 手元と CI でチェックの結果が食い違うことが起きたら、バージョンの固定のしかたを見直す
