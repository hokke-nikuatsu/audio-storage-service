# ADR-0014: 録音のファイルは保存のたびに一意な名前で書き、DB を切り替えてから古いファイルを消す

## 背景と課題

録音はディスクにファイルとして保存し、そのパスを DB に記録する（REQ-5.3、REQ-5.4）。同じユーザーとフレーズの組に再び保存したら置き換え（REQ-1.3）、途中で失敗したら既存の録音を取得できる状態に保つ（REQ-1.7）。置き換えには「ファイルを書く」と「DB を更新する」の2つの書き込みがあり、ディスクと DB は1つのトランザクションにまとめられない。ファイルの名前の付け方と、DB に書くパスを決める必要がある。

## 検討した選択肢

### 組ごとに決まった名前（`{user_id}/{phrase_id}.wav`）で上書きする

- 良い点: 単純で、古いファイルが残らない
- 悪い点: 上書きした後に DB の更新が失敗すると、エラーを返したのにファイルは新しい録音に変わっている。一時ファイルから名前を変えても、DB の失敗との順番の問題は残り、REQ-1.7 を守りにくい

### 保存のたびに一意な名前（`{UUID}.wav`）で書く

- 良い点: DB を新しいパスに切り替えるまで古いファイルに触らないので、どこで失敗しても DB の指す録音は完全なファイルのままになる
- 悪い点: 古いファイルの削除の途中でプロセスが落ちると、どこからも指されないファイルが残る。名前からはどの組の録音か分からない

### 保存のたびに一意な名前を、組のディレクトリの下に書く（`{user_id}/{phrase_id}/{UUID}.wav`）

- 良い点: 一意な名前の利点はそのままで、ディスクを見たときにどの組の録音か分かる
- 悪い点: どこからも指されないファイルが残りうるのは同じ

## 決定

「保存のたびに一意な名前を、組のディレクトリの下に書く」を選ぶ。REQ-1.7 を、ディスクと DB をまたぐトランザクションなしに守れるため。

- 置き換えは「新しいファイルを書く → DB のパスを新しいファイルに切り替える → 古いファイルを消す」の順に行う。DB の切り替えが失敗したら、書いた新しいファイルを消す
- DB には、保存先のルートのディレクトリからの相対パスを書く。ルートは設定で持ち、ルートを移しても DB を書き換えずに済むようにする

## 影響

- 良い点: 録音を履歴として残すように変えるときは、古いファイルを消す手順をやめればよい
- 受け入れたトレードオフ: 古いファイルの削除の前にプロセスが落ちると、どこからも指されないファイルがディスクに残る
- 本番運用なら: DB から指されていないファイルを定期的に探して消す。保存先はオブジェクトストレージにし、ライフサイクルの設定で掃除する

## 見直し条件

- どこからも指されないファイルの量がディスクの容量を圧迫するようになったら、掃除の仕組みを入れる
- 録音を履歴として残す要件が入ったら、古いファイルを消す手順と、対応の表の持ち方を見直す
