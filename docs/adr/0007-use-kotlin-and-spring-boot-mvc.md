# ADR-0007: サービスは Kotlin と Spring Boot で作り、リクエストは Spring MVC で処理する

## 背景と課題

録音の保存と取得を行う HTTP のサービスを作る。multipart で音声ファイルを受け取り、入力を検証し、音声を変換して、データベースとディスクに読み書きする。これを書く言語とフレームワーク、およびリクエストをブロッキングで処理するかノンブロッキングで処理するかを決める必要がある。

## 検討した選択肢

### Kotlin と Spring Boot

- 良い点: multipart の受け取り、入力の検証、データベースへのアクセス、マイグレーションの組み込み、テストの支援がそろっていて、自分で組み合わせを決める部分が少ない。Kotlin は null 安全で、data class で値を短く書ける
- 悪い点: 起動が遅く、メモリも多く使う。自動設定が多く、裏で何が起きているかがコードから見えにくい

### Kotlin と Ktor

- 良い点: 軽く、何をしているかがコードに明示される。Kotlin のために作られている
- 悪い点: DI、データベースへのアクセス、マイグレーション、入力の検証を自分で選んで組む必要があり、決めることと書くコードが増える

### Java と Spring Boot

- 良い点: Spring の部品をそのまま使える
- 悪い点: null 安全がなく、同じことを書いてもコードが長くなる

### リクエストの処理を Spring WebFlux（ノンブロッキング）にする

- 良い点: 少ないスレッドで多くの同時接続をさばける。待ちの多い外部呼び出しや、応答を少しずつ流して返す処理に向く
- 悪い点: 待つ処理がすべてノンブロッキングでないと利点がない。このサービスで待つのは音声を変換する外部のプロセスと JDBC で、どちらもブロッキングである。コードを `Mono` や `Flux`、またはコルーチンで書く必要があり、テストとデバッグが難しくなる

## 決定

「Kotlin と Spring Boot」を選び、リクエストは Spring MVC（ブロッキング）で処理する。必要な部品がそろっているので、自分で決めて組む部分を減らし、録音の保存と取得の振る舞いに集中できるため。このサービスで待つ処理はすべてブロッキングなので、WebFlux にしても利点がなく、複雑さだけが増える。

## 影響

- 良い点: リクエストの処理を上から順に読めるコードで書け、テストも普通の関数呼び出しで書ける
- 受け入れたトレードオフ: 起動時間とメモリの使用量が大きい。自動設定に頼る部分は、設定とテストで振る舞いを確かめる必要がある
- 本番運用なら: 同時に変換するリクエストが増えたときは、仮想スレッドを有効にしてスレッドの占有を和らげ、変換の同時実行数に上限を設ける

## 見直し条件

- 外部 API の呼び出しや、応答を少しずつ流して返す処理が、サービスの主な処理になったら WebFlux を検討する
- 起動時間がデプロイやスケールの要件を満たせなくなったら、ネイティブイメージや軽いフレームワークを検討する
