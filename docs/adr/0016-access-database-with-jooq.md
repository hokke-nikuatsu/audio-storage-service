# ADR-0016: データベースへのアクセスは、スキーマから生成した jOOQ のコードで行う

## 背景と課題

SQLite（ADR-0015）に対して、ID の有無の確認、録音のパスの読み出し、パスの upsert を行う。表や列の名前と型の誤りを実行する前に見つけ（型安全）、値を SQL に連結しないこと（SQL インジェクション対策）を、書く人の注意ではなく道具で守りたい。Kotlin から SQL を発行する方法を決める必要がある。

## 検討した選択肢

### Spring の JdbcClient

- 良い点: SQL をそのまま書け、依存が増えない
- 悪い点: SQL は文字列なので、表や列の誤りは実行するまで分からない。値を文字列で連結する書き方もできてしまう

### Spring Data JPA（Hibernate）

- 良い点: エンティティのプロパティは型安全で、パラメータはバインド変数で渡る
- 悪い点: JPQL は文字列で、型安全に書く Criteria API は冗長。SQLite 向けの部品（方言）は Hibernate 本体になく、別のライブラリが要る。upsert は標準の機能になく、SQL を文字列で書く必要がある。表の形をエンティティにもう一度書くので、DB との食い違いは実行時まで分からない

### Exposed

- 良い点: Kotlin の DSL で型安全に書け、値はバインド変数で渡る
- 悪い点: 表の定義を Kotlin で手で書くので、マイグレーションの SQL との食い違いはコンパイルで分からない

### jOOQ

- 良い点: マイグレーションを流した DB のスキーマから Kotlin のコードを生成するので、列の名前や型が DB と食い違えばコンパイルエラーになる。DSL の値はすべてバインド変数で渡る。SQLite と upsert に対応し、Spring の `@Transactional` がそのまま効く
- 悪い点: ビルドにコード生成の手順が加わる

## 決定

「jOOQ」を選ぶ。型の出どころが DB のスキーマそのものなので、DB とコードの食い違いをコンパイルで止められ、値はいつもバインド変数で渡るため。

- コードの生成は、ビルドの中で一時的な SQLite のファイルにマイグレーションを流し、それを読んで行う。DB のサーバーは要らない
- 生成したコードと jOOQ への依存は `adapter` のモジュールにだけ置く（ADR-0011）

## 影響

- 良い点: スキーマを変えたとき、直す必要のあるコードをコンパイラが示す
- 受け入れたトレードオフ: ビルドがマイグレーションの SQL と jOOQ のコード生成に依存し、最初のビルドが遅くなる

## 見直し条件

- サーバー型の DB に移すとき（ADR-0015 の見直し条件）は、コード生成の入力をその DB に合わせて変える
