# ADR-0019: テストは層ごとに確かめることを分け、業務の分岐はフェイクで、外の世界は本物で確かめる

## 背景と課題

すべての部分を網羅する単体テストは求められていないので、どこを厚く、どこを薄くテストするかを決める必要がある。層は内と外に分かれ、外の世界（DB、ディスク、変換）はポートの向こうにある（ADR-0010）。業務の分岐、外の世界との結合、HTTP との対応、Docker での起動を、どのテストで確かめるかを決める。

## 検討した選択肢

### ポートの偽物をモックのライブラリ（MockK など）で作る

- 良い点: 偽物のクラスを手で書かずに済む
- 悪い点: 振る舞いの指定がテストごとに散らばり、何を偽っているかが読み取りにくい。依存が増える

### ポートの偽物（フェイク）を手で書く

- 良い点: ポートは3つだけで、短く書ける。「保存に失敗する」のような振る舞いがクラス名と中身で読める
- 悪い点: ポートを変えると、フェイクも直す必要がある

### Controller をモックで切り出したテストも書く

- 良い点: エラーとステータスコードの対応を、全体を起動せずに確かめられる
- 悪い点: 全体を起動するテストと確かめることが重なる

## 決定

層ごとに確かめることを分け、モックのライブラリは入れずにフェイクを手で書く。業務の分岐はフェイクで速く網羅し、外の世界との結合は本物でしか確かめられないため。

- application: ポートにフェイクを渡す単体テストで、業務の分岐（REQ-1.3、REQ-1.7、REQ-2.2、REQ-3 など）を網羅する。ここを一番厚くする
- adapter: 本物を使う結合テスト。一時的な SQLite のファイルに Flyway を流し、ffmpeg を本物で起動し、ディスクは一時ディレクトリを使う
- web と全体: Spring Boot を起動し、本物の SQLite・ffmpeg・一時ディレクトリで HTTP を送るテストを少しだけ書く
- Docker: テストは書かず、Dockerfile を作る PR と提出の前に、課題の `curl` の手順を手で流して確かめる。Dockerfile はほとんど変わらず、CI のジョブを作って保つ手間に見合わないため
- domain の値のテストと、Controller を切り出したテストは書かない
- テストを走らせるホストには ffmpeg を入れる（手元は各自、CI は `apt`）。見つからなければ、飛ばさずに分かるメッセージで落とす。黙って飛ばすと、確かめていないのに通ったように見えるため

## 影響

- 良い点: 業務の分岐のテストは速く、外の世界のテストは本物との食い違いを拾える
- 受け入れたトレードオフ: 開発の準備に ffmpeg が加わる。ホストと Docker の中で ffmpeg のバージョンがずれうるが、Docker での手の確認で拾う
- 本番運用なら: イメージを起動して確かめるテストを CI に入れる。カバレッジの基準、負荷のテスト、クライアントとの契約のテストを足す

## 見直し条件

- ホストの ffmpeg とイメージの ffmpeg の違いで、手元と CI の結果が食い違うことが起きたら、テストを Docker の中で走らせる
