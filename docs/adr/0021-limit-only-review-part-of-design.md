# ADR-0021: design.md の行数の上限は、人がレビューする前半だけに掛ける

## 背景と課題

ADR-0002 では、design.md 全体を目安200行・上限250行とした。上限の目的は、人がレビューで上から読み切れる長さに保つことで、design.md は `---` の区切りの行より上が人のレビューする部分、下が実装の参照（Components and Interfaces、File Structure Plan）になっている。最初の design.md を書いたところ、全体を上限に収めるために実装の参照を詰めることになり、1行に複数のファイルやコンポーネントが並んで読みにくくなった。上限をどこに掛けるかを決め直す必要がある。

## 検討した選択肢

### 前半だけに上限を掛ける

- 良い点: 上限の目的（レビューの負担）をそのまま守れる。実装の参照を、1行に1ファイルの読みやすい形で書ける
- 悪い点: 実装の参照が際限なく長くなりうる

### 全体の上限を上げる

- 良い点: 変えるのが数字だけで済む
- 悪い点: レビューする前半が長くなるのを止められない

### design.md を前半と後半の2つのファイルに分ける

- 良い点: レビューする部分と実装の参照が、ファイルで分かれる
- 悪い点: cc-sdd の skill が両方のファイルを読むよう、テンプレートとルールを広く直す必要がある

## 決定

「前半だけに上限を掛ける」を選ぶ。上限で守りたいのは人がレビューする部分の長さで、実装の参照は詰めるより読みやすく書くほうが、タスクの生成と実装の役に立つため。ADR-0002 のうち design.md の行数の判断だけを変え、ほかの決定は有効なまま。

- 前半と後半の境目は、`---` の区切りの行ではなく `# Implementation References` の見出しで示す。`---` は Markdown のどこにでも書けてチェックが取り違えやすく、読む人にも境目として目立たないため
- 見出しより上を、目安150行・上限200行にする
- 見出しより下には上限を設けない。その代わり、表は1行に1コンポーネント、File Structure Plan は1行に1ファイルで書く
- 行数のチェックは、design.md の見出しより上だけを数える。見出しがなければ全体を数える

## 影響

- 良い点: 前半の長さはこれまでより厳しく保たれ、後半は読みやすく書ける
- 受け入れたトレードオフ: 実装の参照の長さは、レビューで見るしかない

## 見直し条件

- 見出しより下が前半より長くなる design.md が続いたら、後半にも上限を設けるか、2つのファイルに分ける案を再検討する

## 反映先

- `.kiro/settings/templates/specs/design.md`（行数のルールと境目の見出し）
- `.claude/skills/kiro-spec-design/rules/design-principles.md`（前半と後半の分け方）
- `scripts/checks/doc_line_count.py`（行数のチェック）
