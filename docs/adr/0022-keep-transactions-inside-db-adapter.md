# ADR-0022: トランザクションは DB のアダプタの中だけで張り、application では張らない

## 背景と課題

ADR-0010 と ADR-0011 では、`application` で Spring の `@Transactional` を使ってよいとし、`application` に `spring-tx` を入れることにした。実装では、保存で1つにまとめる必要のある DB の操作（古いパスの読み出しと、新しいパスの書き込み）を、DB のアダプタの `replacePath` の中の jOOQ のトランザクションで閉じ、`application` では `@Transactional` を使わなかった。規約が実装より広い依存を許したままだと、後でユースケースに `@Transactional` を付ける変更を規約の上で止められないので、どちらに合わせるかを決める必要がある。

## 検討した選択肢

### application で `@Transactional` を使ってよいままにする

- 良い点: 複数のポートの呼び出しを、ユースケースで1つのトランザクションにまとめられる
- 悪い点: SQLite への接続は1本なので、ユースケースのメソッドでトランザクションを張ると、ffmpeg の変換（最大30秒）が終わるまで接続を持ち続け、ほかの保存と取得がすべて待たされる

### DB のアダプタの中だけで張る

- 良い点: トランザクションは DB を使う間だけになり、変換の間に接続を持たない。トランザクションを張る場所が1か所に決まる
- 悪い点: トランザクションの単位が、ポートのメソッド1つに固定される

## 決定

「DB のアダプタの中だけで張る」を選ぶ。1本の接続を変換の間に持ち続けると、ほかの要求がすべて待たされるため。

- ADR-0010 の「`application` では `@Transactional` を使ってよい」と、ADR-0011 の「`application` に `spring-tx` を入れる」を変える。`application` が依存してよい Spring は `spring-context`（`@Service`）だけにする
- ADR-0010 と ADR-0011 のほかの決定は有効なまま

## 影響

- 良い点: 保存の変換が長くかかっても、ほかの要求の DB の操作は待たされない
- 受け入れたトレードオフ: 複数のポートの呼び出しを1つのトランザクションにまとめたくなったら、ポートのメソッドを1つにまとめ直す

## 見直し条件

- 複数のポートの呼び出しを、1つのトランザクションにまとめる必要のある要件が出たとき
- DB を、複数の接続を持てるもの（PostgreSQL など）に変えたとき
