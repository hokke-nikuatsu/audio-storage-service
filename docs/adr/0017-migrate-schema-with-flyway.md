# ADR-0017: スキーマは Flyway の SQL のマイグレーションで管理し、初期データは別の場所に置く

## 背景と課題

SQLite のスキーマ（ADR-0015）は、サービスの起動時に作り、ビルドの中では jOOQ のコード生成の入力にする（ADR-0016）。また、有効なユーザー ID とフレーズ ID は、サービスの外で決まり、起動時の初期データとして用意される（REQ-4.2）。スキーマの変更を履歴として残しながら、この3つの用途で同じ定義を使う方法を決める必要がある。

## 検討した選択肢

### Flyway

- 良い点: 素の SQL のファイルを番号順に流すだけで、何が流れるかがファイルを見れば分かる。SQLite に本体（`flyway-core`）で対応し、Spring Boot の起動時に自動で流せる。jOOQ のコード生成の前に流す組み合わせも定番
- 悪い点: 取り消しの SQL は無償版にない

### Liquibase

- 良い点: DB に依存しない形で書け、取り消しも書ける
- 悪い点: 表3つには重い。素の SQL で書くなら Flyway と変わらない

### Spring Boot の `schema.sql`

- 良い点: 道具が要らない
- 悪い点: 番号も履歴もなく、表を変えるときに既存のデータを持った DB を移行する手段がない

## 決定

「Flyway」を選ぶ。素の SQL で書け、サービスの起動と jOOQ のコード生成の両方で同じファイルを流せるため。

- 取り消すときは、戻す内容の新しいマイグレーションを足す
- 初期データはスキーマと別の場所（`db/seed`）に置き、流すかどうかを設定で切り替える。手元の Docker では流し、jOOQ のコード生成にはスキーマ（`db/migration`）だけを使う。試験用の ID を、本番の DB に入れないため

## 影響

- 良い点: スキーマの変更がコードと同じ PR でレビューされ、DB に流した履歴が残る
- 受け入れたトレードオフ: 初期データの場所を切り替える設定が1つ増える
- 本番運用なら: 有効なユーザー ID とフレーズ ID の表は、初期データではなく、会員登録や教材の追加を知らせるイベントを受けて更新する

## 見直し条件

- サーバー型の DB に移すとき（ADR-0015 の見直し条件）は、マイグレーションの SQL をその DB の方言に合わせて書き直す
