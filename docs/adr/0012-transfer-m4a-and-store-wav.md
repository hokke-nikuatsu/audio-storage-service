# ADR-0012: 送受信は m4a（AAC）、保存は WAV（PCM 16 ビット）にする

## 背景と課題

音声のフォーマット（m4a、WAV など）は、音を数値にする方式（コーデック）と、それを入れる箱（コンテナ）の組み合わせで、m4a は MP4 のコンテナに AAC を、WAV は WAV のコンテナに PCM を入れたものである。コーデックには、音の情報を落とさないもの（PCM は圧縮なし、FLAC は可逆圧縮）と、聞き取りにくい部分を捨てて小さくする非可逆圧縮のもの（AAC、Opus）がある。非可逆圧縮で捨てた情報は、元に戻せない。

サービスは、クライアントと送受信するフォーマットと、サーバーのディスクに保存するフォーマットの2つだけを扱う。クライアントはモバイル端末で、録音を送り、あとで聞き返すために取り出す。保存と取得では「送受信用 → 保存用 → 送受信用」と変換するので、非可逆圧縮を重ねると変換のたびに音質が落ちる（世代劣化）。

## 検討した選択肢

### 送受信用: m4a（MP4 のコンテナに AAC）

- 良い点: iOS（`AVAudioRecorder`）と Android（`MediaRecorder`）の標準の録音の API で作れ、クライアントは録音を変換せずに送れる。非可逆圧縮で小さく、モバイルの回線に向く
- 悪い点: 非可逆圧縮なので、元の録音の時点で音の情報の一部が落ちている

### 送受信用: Opus（Ogg や WebM のコンテナに Opus）

- 良い点: 人の声を小さく圧縮しても音質を保ちやすく、AAC より小さい
- 悪い点: iOS の標準の録音では作りにくい

### 保存用: WAV（WAV のコンテナに PCM 16 ビット）

- 良い点: 圧縮しないので、音の情報を落とさない。最も単純で、どの道具でも読め、音声の解析や認識にそのまま渡せる
- 悪い点: 大きい（1秒間に 44,100 回音を測るモノラルの録音で、1分あたり約 5MB）

### 保存用: FLAC（FLAC のコンテナに FLAC）

- 良い点: 可逆圧縮なので音の情報を落とさず、WAV の半分程度の大きさになる
- 悪い点: 読むのに、圧縮を戻す道具（デコーダ）が要る

### 保存用: Opus（Ogg のコンテナに Opus）

- 良い点: 最も小さい
- 悪い点: 非可逆圧縮なので、取得のたびに「AAC → Opus → AAC」と劣化が積み重なる

## 決定

送受信用は「m4a（AAC）」、保存用は「WAV（PCM 16 ビット）」を選ぶ。クライアントが標準の録音をそのまま送れ、保存の段階で音の情報を何も落とさないため。WAV は FLAC より大きいが、練習フレーズの録音は数秒から十数秒で1件 1MB 前後なので、大きさより単純さを取る。

- サンプリングレート（1秒間に音を測る回数）とチャンネル数（モノラルなら 1、ステレオなら 2）は、元の録音のまま保つ。録音はユーザーが聞き返すためのもので、音質を落とさないため
- 取得の `{audio_format}` で受け付けるのは `m4a` だけにする

## 影響

- 良い点: 保存した録音は、解析や認識のような別の用途にも、変換せずに渡せる
- 受け入れたトレードオフ: ディスクの使用量が m4a のまま持つより約10倍になる。取得のたびに AAC への変換が要る

## 見直し条件

- 音声認識の入力として使うことが決まったら、サンプリングレートとチャンネル数をそろえるかを見直す
- クライアントが Opus など別のフォーマットで送る必要が出たら、送受信用のフォーマットを増やす
