# ADR-0011: 層の依存の向きは、層ごとの Gradle のモジュールで強制する

## 背景と課題

ポートとアダプタの構造（ADR-0010）では、依存が外から内へ向く。しかし、決めた向きを Kotlin のコンパイラは知らず、`application` が `adapter` のクラスを直接 import してもコンパイルもテストも通る。AI と人が書くコードで、依存の向きが崩れたことを機械で止める方法を決める必要がある。

## 検討した選択肢

### 1つのモジュールでパッケージを分け、ArchUnit のテストで確かめる

- 良い点: ビルドの設定が1つで済む。クラス名やアノテーションを置く場所のような、モジュールの中の規則も書ける
- 悪い点: 違反はテストを走らせるまで分からない。規則をテストとして書き、保つ必要がある

### 1つのモジュールでパッケージを分け、Konsist のテストで確かめる

- 良い点: Kotlin のソースを読むので、Kotlin 特有の書き方も規則にできる
- 悪い点: Kotlin のコンパイラを中に持つので、使う Kotlin（2.3 系）への追従を確かめる必要がある

### 層ごとに Gradle のモジュールを分ける

- 良い点: 使ってよいモジュールだけを依存に書くので、違反する import はコンパイルエラーになり、IDE の補完にも出ない。外部ライブラリもモジュールごとに制限できる。モジュールの依存を見ればアーキテクチャが読める。Kotlin の `internal` で、アダプタの中のクラスを外から隠せる
- 悪い点: `build.gradle.kts` が層の数だけ要り、共通の設定をまとめる仕組みが要る。Spring Boot を起動して部品を組み立てるモジュールが別に要る。モジュールの中の規則は確かめられない

## 決定

「層ごとに Gradle のモジュールを分ける」を選ぶ。確かめたい規則がすべてモジュールの単位で表せ、違反をテストより早いコンパイルの時点で、道具を足さずに止められるため。

- モジュールは `domain`、`application`、`adapter`、`web`、`bootstrap` の5つにする。DB、ディスク、変換のアダプタは、`adapter` の中のパッケージで分ける
- `domain` は外部のライブラリに依存しない。`application` には `spring-context` と `spring-tx` だけを入れ、Spring Web と JDBC を入れない（ADR-0010）
- ほかのモジュールへの依存は `implementation` で宣言し、`api` は `application` から `domain` への依存だけに使う。`api` の依存は使う側にも推移的に見え、隠したい依存が漏れるため
- モジュールごとに依存してよいモジュールの表を `build-logic` に1か所だけ書き、表にない依存（テストの依存を含む）を宣言したらビルドを失敗させる。規則が各モジュールの `build.gradle.kts` にしかないと、依存を1行足すだけで素通りするため
- モジュールに共通の設定（Kotlin、toolchain、ktlint、detekt）は、`build-logic` の convention plugin にまとめる。モジュールごとに同じ設定を書かないため

## 影響

- 良い点: 依存の向きのためのテストと道具が要らない。規則を変えるには `build-logic` の表を変える必要があり、その変更がレビューに出る
- 受け入れたトレードオフ: ビルドの設定のファイルが増え、1つのモジュールより最初のビルドが遅い。依存の表を検査するコードを `build-logic` に持つ。`bootstrap` はすべてに依存するので、組み立て以外の処理を書かないことはレビューで見る

## 見直し条件

- アダプタどうしの依存（DB のアダプタが変換のアダプタを使うなど）が問題になったら、`adapter` をアダプタごとのモジュールに分ける
- クラス名やアノテーションの置き場のような、モジュールの中の規則が必要になったら、ArchUnit を足す
