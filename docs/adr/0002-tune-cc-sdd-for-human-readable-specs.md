# ADR-0002: cc-sdd はテンプレートを主にチューニングし、design.md を人が読める長さと構成に保つ

## 背景と課題

cc-sdd（v3.1.0）の既定の design テンプレートは332行あり、1000行に近づくまで警告しない。設計ルールも技術スタックの表やコンポーネントごとの詳細な記述を求めるため、既定のままでは design.md が肥大化し、人がレビューできる文書にならない。チューニングの手段（テンプレート、ルール、steering、SKILL.md 本体）のどこに手を入れるかを決める必要がある。

## 検討した選択肢

### 既定のまま使う

- 良い点: 手間がかからず、アップグレードも容易
- 悪い点: design.md が肥大化し、人のレビューが形だけになる

### テンプレートを主に作り直し、ルールは矛盾する箇所だけ書き換える

- 良い点: 公式のカスタマイズガイドが想定する方法で、design.md は「ファイルが存在すること」以外に構造の制約がない。文書の構成と長さを直接決められる
- 悪い点: アップグレードでテンプレートとルールが上書きされるため、変更を管理する必要がある

### SKILL.md 本体まで書き換える

- 良い点: 要件 ID の書式や research.md の生成など、テンプレートでは変えられない挙動も変えられる
- 悪い点: 数字の要件 ID などの前提が複数の SKILL.md にまたがっていて、変更箇所が多い。アップグレードのたびに壊れ、生成が途中で停止する危険がある

### design を基本設計と詳細設計の2ファイルに分ける

- 良い点: 人がレビューする文書と、実装が参照する文書を完全に分けられる
- 悪い点: 1つの機能に2つの設計書は過剰で、両者の整合を保つ手間が増える

## 決定

「テンプレートを主に作り直し、ルールは矛盾する箇所だけ書き換える」を選ぶ。内容は次のとおり。

- design テンプレートを、前半を人がレビューする部分、後半を実装の参照に並べ替える
- 長さは200行以内を目安とし、250行を上限とする
- 技術スタックの表は書かない。技術の選定は steering と ADR に書き、design では ADR 番号で参照する
- 構成・順番・行数の上限はテンプレートだけに書く。既定のルールのうちテンプレートと矛盾する箇所は、打ち消す指示を足すのではなく元の文を直接書き換え、矛盾をなくす。書き換えた箇所には `project-override` の印を付ける
- SKILL.md 本体は書き換えない
- 見出しは英語のまま、本文は日本語で書く
- 要件 ID は cc-sdd の前提どおり数字（`1.2`）のままにする。cc-sdd の文書の外（テスト名、PR、ADR、コミット）では `REQ-1.2` と書き、requirements.md の該当 ID を指す
- 人がレビューするのは requirements.md と design.md だけにし、spec.json・research.md・tasks.md は対象にしない

## 影響

- 良い点: design.md が上から順に読める長さと構成になり、要件・コンポーネント・テストの対応が1つの表で追える
- 受け入れたトレードオフ: cc-sdd をアップグレードすると、チューニングしたテンプレートとルールが上書きされる。アップグレード後は `project-override` の印と git の差分を手がかりに再適用する
- 本番運用なら: チューニングしたテンプレートとルールをチームで共有し、cc-sdd のアップグレード時に差分を確認する手順を決める

## 見直し条件

- ルールを書き換えても、生成された design.md が250行を超えることが続いたら、design を2ファイルに分ける案を再検討する
- cc-sdd のアップグレードでテンプレートやルールの構成が変わり、再適用で対応できなくなったら、バージョンを固定し続けるか乗り換えるかを再検討する

## 反映先

- `.kiro/settings/templates/specs/design.md`
- `.claude/skills/kiro-spec-design/rules/design-principles.md` と `design-review-gate.md` の `project-override` の印を付けた箇所
- 要件 ID の書き方は AGENTS.md（ADR-0003 で作成）
