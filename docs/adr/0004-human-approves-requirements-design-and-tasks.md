# ADR-0004: cc-sdd の spec は、要件・設計・タスクの3つを人が承認する

## 背景と課題

ADR-0001 では要件と設計を人が承認するとし、ADR-0002 では人がレビューする spec を requirements.md と design.md に限った。しかし cc-sdd は tasks.md が承認されないと実装に進まないため、tasks.md を人が見ないなら `-y` で自動承認するしかなく、承認を飛ばさない方針と食い違う。タスクの分け方は実装の PR の単位を決めるので、人が確認しないまま実装に入ってよいかを決める必要がある。

## 検討した選択肢

### tasks.md は人がレビューせず、`-y` で自動承認する

- 良い点: 承認の手間が1回減る。タスクは承認済みの設計から導かれる
- 悪い点: タスクの粒度や順番の問題に、実装の PR を出すまで気づけない。分け方が悪いと、複数の PR をまとめてやり直すことになる

### tasks.md も人が承認する

- 良い点: 実装に入る前に、PR の単位（粒度・順番・要件の網羅）を人が確認できる。cc-sdd の承認の流れをそのまま使え、`-y` を使わずに済む
- 悪い点: 承認の手間が1回増える

## 決定

「tasks.md も人が承認する」を選ぶ。タスクの分け方は実装の PR の単位をそのまま決めるため、誤りを実装の前に見つけるほうがやり直しが小さい。

- 人が承認する spec は requirements.md、design.md、tasks.md の3つにする。spec.json と research.md はレビューの対象にしない
- tasks.md の承認では、設計は承認済みなので分け方だけを見る（1タスクが1つの PR に収まる粒度か、依存関係に沿った順番か、すべての要件がどれかのタスクに入っているか）
- この決定は、ADR-0001 の「要件と設計は人が承認する」と、ADR-0002 の「人がレビューするのは requirements.md と design.md だけ」を変更する。両 ADR のほかの決定は有効なまま

## 影響

- 良い点: 要件・設計・タスクのすべての段階で、人の承認を経てから次へ進む
- 受け入れたトレードオフ: 実装に入るまでの承認が1回増える

## 見直し条件

tasks.md の承認で直す点がない状態が続き、タスクの分け方が実装の PR で問題になったこともなければ、tasks.md の承認を省く案を再検討する。
