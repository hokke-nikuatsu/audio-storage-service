# ADR-0001: cc-sdd による仕様駆動で、AI が実装・レビューし、人が判断する開発プロセスにする

## 背景と課題

実装には AI を使う。AI の出力をどの基準で受け入れ、何を却下したかを、後からたどれる形で残せる開発プロセスが必要になる。

## 検討した選択肢

### 仕様駆動（cc-sdd）で、AI が実装・レビューし、人が判断する

- 良い点: 要件・設計を人が承認してから実装に入るので、AI の出力を判断する基準が文書として残る
- 悪い点: 仕様を書く分、実装に入るまでの時間が増える。cc-sdd には spec が肥大化し、人が読みにくくなるという既知の問題がある（対策は ADR-0002 に記録する）

### 仕様を書かずに AI に直接実装させる

- 良い点: 最も早く動くものができる
- 悪い点: 何を基準に AI の出力を受け入れたかが残らず、判断を後から検証できない

### 人が手で実装し、AI は補助に使う

- 良い点: 実装の細部をすべて人が把握できる
- 悪い点: 実装に時間がかかる。AI の出力をどう受け入れたかを仕組みとして残せない

## 決定

「仕様駆動（cc-sdd）で、AI が実装・レビューし、人が判断する」を選ぶ。流れは次のとおり。

1. cc-sdd で要件 → 設計 → タスクを作り、要件と設計は人が承認する
   - 要件は実装の技術に依存させない。言語・フレームワークを含む技術選定は、要件の承認後に設計の段階で行い、判断ごとに ADR を書く
2. タスクごとに AI が実装し、lefthook と CI で機械的に確認する
3. AI が PR 単位でレビューする（観点ごとの並列レビューと、指摘の裏取り）。AI は approve しない
4. 人が PR の「人の判断」欄に指摘への対応を書き、マージする

1人で開発するリポジトリでは GitHub 上で自分の PR を approve できないため、**「人の判断」欄を書いてからマージすることを approve とみなす。**

## 影響

- 良い点: AI の出力をどの基準で受け入れ、何を却下したかが、要件・設計・PR に残る
- 受け入れたトレードオフ: 仕様とレビューの分、実装に使える時間が減る
- 本番運用なら: チームでは GitHub の approve を必須にし、AI レビューは CI のボットとして PR ごとに自動で動かす

## 見直し条件

- AI レビューの指摘のうち、裏取りで取り下げたものが半数を超える PR が続いたら、レビューの観点と分け方を見直す
- 承認時に人が書き直した量が spec の半分を超えたら、cc-sdd のチューニングを見直す

## 反映先

- AGENTS.md と steering の開発の流れ（フェーズ0で作成）
- cc-sdd の運用方法は ADR-0002 に記録する
