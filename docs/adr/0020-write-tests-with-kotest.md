# ADR-0020: テストは Kotest で書く

## 背景と課題

テストは、ユースケースの単体テストを一番厚くし、Spring Boot を起動するテストは少しだけ書く（ADR-0019）。テストの名前には要件 ID を書き、要件と受け入れ条件の構造で並べたい。テストのフレームワークとアサーションの道具を決める必要がある。

## 検討した選択肢

### JUnit 5 と AssertJ

- 良い点: Spring Boot の標準で、追加の依存がない。Spring のテストの仕組みがそのまま使える
- 悪い点: Kotlin らしい書き方にはならない

### JUnit 5 と Kotest のアサーション

- 良い点: Spring のテストの仕組みはそのまま使え、確かめる部分は `shouldBe` のように Kotlin らしく書ける
- 悪い点: テストの入れ子やデータ駆動の書き方は JUnit のまま

### Kotest（フレームワークとアサーション）

- 良い点: Kotlin のために作られている。テストを入れ子にでき、要件 → 受け入れ条件の構造をそのまま書ける。データ駆動のテストも書きやすい
- 悪い点: Spring のテストの仕組みは JUnit 5 を前提にしていて、Spring 用の拡張を通して使う。IntelliJ で個別のテストを走らせるには Kotest のプラグインが要る

## 決定

「Kotest（フレームワークとアサーション）」を選ぶ。一番厚く書くユースケースの単体テストは Spring を使わないので Kotest の書きやすさがそのまま効き、Spring を起動するテストは少ないので拡張を通す手間も小さいため。

- テストは `context` で要件を、`test` で受け入れ条件を表し、名前に要件 ID（`REQ-1.3` など）を書く
- Spring Boot を起動するテストは、`kotest-extensions-spring` を通して書く

## 影響

- 良い点: テストの並びが requirements.md の構造と対応し、どの受け入れ条件を確かめているかが名前から分かる
- 受け入れたトレードオフ: Spring のテストの情報の多くは JUnit 5 で書かれていて、Kotest に読み替える必要がある

## 見直し条件

- Kotest が Kotlin 2.3 と Spring Boot 4.1 の組み合わせで動かなければ、JUnit 5 と Kotest のアサーションに切り替える
- Spring を起動するテストが増え、拡張を通す手間が目立つようになったら、同じく切り替える
