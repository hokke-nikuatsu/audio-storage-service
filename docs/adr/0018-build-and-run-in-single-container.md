# ADR-0018: Dockerfile の中でビルドし、Ubuntu ベースの1つのコンテナで動かす

## 背景と課題

サービスと DB を、Dockerfile を使って手元のマシンで起動し（REQ-4.1）、ポートを指定しない `http://localhost/` で受け付ける（REQ-5.1）。コンテナには Java 25 の実行環境と ffmpeg・ffprobe（ADR-0013）が要り、SQLite のファイル（ADR-0015）と録音のファイルは、コンテナを作り直しても残す必要がある。どこでビルドし、どのイメージの上で、どう起動するかを決める。

## 検討した選択肢

### ビルド: Dockerfile の中でビルドする（マルチステージ）

- 良い点: Docker だけで動かせ、手元に JDK も Gradle も要らない。ビルドの段は JDK 25 の入ったイメージなので、Gradle の toolchain（ADR-0008）はその JDK を使う
- 悪い点: イメージのビルドに Gradle のビルドの時間が加わる

### ビルド: 手元でビルドした jar をコピーする

- 良い点: Dockerfile が単純になる
- 悪い点: 先に手元で Gradle のビルドを走らせる必要があり、Docker だけでは動かせない

### イメージ: Alpine（musl）ベースの Temurin

- 良い点: イメージが小さい
- 悪い点: C の標準ライブラリが glibc ではなく musl で、SQLite の JDBC ドライバのようなネイティブのライブラリと相性の問題が出ることがある

### 起動: Dockerfile だけにする

- 良い点: ファイルが1つで済む
- 悪い点: ポートとボリュームを `docker run` の引数で毎回指定する必要があり、間違えやすい

## 決定

Dockerfile の中でマルチステージでビルドし、実行の段は Ubuntu（glibc）ベースの `eclipse-temurin:25-jre` に `apt` で ffmpeg を入れる。起動は、1サービスだけの `compose.yaml` に加えて、`docker build` と `docker run` の手順も README に書く。相手の手元で、Docker だけで確実に動くことを優先するため。

- コンテナの中では root ではないユーザーで 8080 番で待ち受け、ホストの 80 番に割り当てる。アップロードされたファイルを ffmpeg に読ませるので、乗っ取られたときの被害を小さくするため
- `/data` をボリュームにし、DB のファイルと録音のファイルをその下に置く

## 影響

- 良い点: `docker compose up --build` の1つのコマンドで、初期データの入ったサービスが起動する
- 受け入れたトレードオフ: Alpine より大きなイメージになる。最初のイメージのビルドに時間がかかる
- 本番運用なら: CI でイメージをビルドしてレジストリに置き、録音はボリュームではなくオブジェクトストレージに置く

## 見直し条件

- イメージの大きさが、配布や起動の時間で問題になったら、ベースのイメージを見直す
