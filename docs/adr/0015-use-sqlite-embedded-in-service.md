# ADR-0015: データベースはサービスに組み込む SQLite にする

## 背景と課題

DB には、有効なユーザー ID の表、有効なフレーズ ID の表、録音のパスとユーザー ID・フレーズ ID の対応の表の3つを持つ（REQ-5.4）。課題が求めるのは、サービスが含むシンプルな DB で、サービスと DB は1つの Dockerfile で手元のマシンで起動できればよく（REQ-4.1）、本番レベルの品質は求めていない。一方で、録音の置き換えでは、組で1行の形を一意制約と upsert で守り、パスの切り替えを1つのトランザクションで行う（ADR-0014）。どの DB を使うかを決める必要がある。

## 検討した選択肢

### SQLite（ファイル）

- 良い点: サービスのプロセスの中で動き、別のコンテナが要らないので、Dockerfile 1つで起動できる。外部キー、一意制約、upsert（`ON CONFLICT`）、トランザクションがそろい、DDL もトランザクションに入る。DB は1つのファイルで、テストも一時ファイルで速く動く
- 悪い点: 書き込みは同時に1つだけ。外部キーは接続ごとに有効にする設定が要る。Spring Data JDBC は SQLite の方言を標準で持たない

### H2（ファイル）

- 良い点: Java で書かれていて、Spring Boot の対応が厚い
- 悪い点: DB のファイルが H2 の独自の形式で、H2 の jar を使う道具でしか開けない。SQLite なら、macOS や多くの Linux に最初から入っている `sqlite3` のコマンドで中身を確かめられる

### PostgreSQL

- 良い点: 機能がそろい、同時の書き込みにも強く、本番に近い
- 悪い点: 別のコンテナと、それを起動する Docker Compose が要り、DB の準備を待つ仕組みも要る。この規模のサービスには重い

## 決定

「SQLite（ファイル）」を選ぶ。必要な機能（外部キー、一意制約、upsert、トランザクション）がそろい、サービスに組み込めて、Dockerfile 1つで起動できるため。同時の書き込みは1つだけになるが、書き込みは録音の保存のたびに1行で、変換の時間に比べて短い。

- 外部キーの検査は、接続ごとに有効にする
- DB のファイルは、録音のファイルと同じく、コンテナを作り直しても残る場所に置く（置き方は実行環境の判断で決める）

## 影響

- 良い点: DB のための別のコンテナ、接続先の設定、起動の待ち合わせが要らない
- 受け入れたトレードオフ: サービスを複数のインスタンスに増やせない（DB のファイルを共有できない）。書き込みが重なると待ちが生じる
- 本番運用なら: PostgreSQL などのサーバー型の DB（マネージドサービス）を使い、サービスを複数のインスタンスで動かす

## 見直し条件

- サービスを複数のインスタンスで動かす必要が出たら、サーバー型の DB に移す
- 書き込みの待ち（`SQLITE_BUSY`）による失敗や遅延が観測されたら、サーバー型の DB に移す
