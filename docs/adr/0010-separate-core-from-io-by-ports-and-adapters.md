# ADR-0010: 業務の手順と外の世界をポートとアダプタで分ける

## 背景と課題

録音の保存は「ID を確かめる → 音声を変換する → ファイルに保存する → パスを DB に記録する」という手順で、取得はその逆である。手順はめったに変わらないが、DB、ディスク、変換の外部プロセスは環境や規模で変わる。手順と技術の詳細を、どう分けてコードに置くかを決める必要がある。

## 検討した選択肢

### Spring の定番の3層（controller → service → repository）

- 良い点: 情報が多く、ファイルが少ない
- 悪い点: DB は Repository 越しに使えるが、ディスクと変換は service から直接呼ぶことになる。手順を試すのに本物の ffmpeg とディスクが要り、「変換に失敗したら既存の録音を残す」（REQ-1.7）のような分岐を試しにくい。保存先を変えるには手順のコードを書き換える

### 内と外を分け、境目をポートとアダプタにする

- 良い点: 手順は、自分が外に求めるもの（ポート）をインターフェースとして宣言し、DB、ディスク、変換はその実装（アダプタ）に閉じ込める。依存は外から内へ向き、手順は技術の詳細を知らない。偽物のアダプタを渡して、失敗の分岐を本物なしで試せる。保存先や変換の方法は、アダプタを足して差し替えられる
- 悪い点: インターフェースとクラスが増える

### Onion アーキテクチャ

- 良い点: DIP で依存を内へ向ける点は、ポートとアダプタと同じ
- 悪い点: 内側を Domain Model、Domain Services、Application Services の層に分けるが、このサービスのドメインは ID と録音の対応くらいしかなく、細かい層分けが効かない

## 決定

「内と外を分け、境目をポートとアダプタにする」を選ぶ。このサービスの中心は外の世界（DB、ディスク、変換）の組み合わせで、そこをインターフェースで切ると、失敗の分岐を試せ、外の世界を差し替えられるため。

- 内側は `domain` と `application` の2つにする。ポートは外の世界との境目（DB、ディスク、変換）にだけ置き、Controller から呼ばれる側の入力のポートは置かない
- `application` では Spring の `@Service` と `@Transactional` を使ってよい。Web と DB の詳細（Spring Web、JDBC）は使わない。Bean の登録とトランザクションを Spring の普通の書き方で済ませるため

## 影響

- 良い点: 保存先を S3 に変える、変換の方法を変えるといった拡張で、変える場所がアダプタに限られる
- 受け入れたトレードオフ: 外の世界ごとにインターフェースと実装の2つのファイルが要る。`application` は Spring から完全には切り離されない

## 見直し条件

- ドメインの規則（録音の履歴、ユーザーごとの上限など）が増え、`application` に業務の判断が溜まり始めたら、内側の層を細かく分ける
- Spring 以外の実行環境（バッチ、CLI）から同じ手順を使う必要が出たら、`application` から Spring のアノテーションを外す
