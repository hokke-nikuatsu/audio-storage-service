# 変更をレビューする

レビューの観点・指摘の書き方・指摘の数・優先度・指摘しない範囲は `docs/conventions/review.md` を正とし、このファイルに複製しない。

## 呼び方

- 引数なし（`/review`）: 「別のセッションを起動する」の手順で、会話の履歴を持たない新しいセッションを起動し、その中で `/review here` を実行させる。自分が書いたコードを同じ文脈でレビューすると甘くなるため、レビューそのものはこの会話では行わない
- `here`（`/review here`）: 「レビューする」の手順で、このセッションの中でレビューする。引数なしの呼び方が起動したセッションの中で使う。会話の中で実装をしていた場合は、レビューせずに止まり、引数なしで呼ぶよう人に伝える

## 前提

- コードを直さない。コミット、プッシュ、GitHub への投稿、approve をしない
- 「マージしてよい」とは書かない。判断は人がする
- モデルの使い分け: 観点ごとの洗い出しはサブエージェント（Sonnet）に任せ、変更の種類の判定と、指摘の検証・確定はこの skill を動かすモデル（Opus）が行う。検証と確定には、コードを読み直して判断する力が要るため

## 別のセッションを起動する（引数なし）

1. 今のブランチ名と HEAD のコミット SHA を記録する
2. Bash ツールを `run_in_background` で使い、次のコマンドを実行する
   ```
   claude -p "/review here" --setting-sources project --model opus --effort high --allowedTools <許可> < /dev/null
   ```
   - `<許可>` には、この skill の front matter の `allowed-tools` から `Bash(claude -p:*)` を除いたものを、1つずつ引数として渡す。新しいセッションの中から、さらにセッションを起動させないため
   - `--setting-sources project` は変えない。ユーザー設定やローカル設定（`.claude/settings.local.json`）に広い許可があると、`--allowedTools` で絞っても新しいセッションとサブエージェントが任意のコマンドを実行できてしまうため。リポジトリにコミットされた設定だけを読むことで、渡した許可だけが効く（書き込みは `.review/` の中だけ、コマンドは読むためのものだけ）
3. 起動したことと、終わるまでこのブランチにコミットしないこと（HEAD が変わると結果が古くなるため）を人に伝え、終了の通知を待つ
4. 終了の通知が来たら、`.review/<ブランチ名>.md`（`/` は `-` に置き換える）を読む。結果に書かれた HEAD が手順1で記録したものと違えば、結果が古いことを伝える。ファイルがない、または起動したコマンドが失敗した場合は、その出力を人に伝えて止まる
5. 指摘の件数と、Critical・High の内容を人に伝える。起動したセッションの出力に、消した古い結果が書かれていれば、それも伝える

## レビューする（`here`）

1. `docs/conventions/review.md` を読む
2. マージ済みのブランチの結果を消す
   - `git fetch --prune` してから、`.review/` にあるファイルごとに、対応するブランチを `git branch -vv` の一覧から決める。ファイル名の `-` は `/` だった可能性がある
   - 上流が `gone` のブランチ（プッシュ後、マージで自動的に削除されたもの）の結果だけを消す。上流のないブランチ（まだプッシュしていないもの）の結果と、対応が決められないファイルは消さずに人に伝える
3. 対象を決め、事前に確かめる
   - 今のブランチに PR があれば `gh pr view --json baseRefName,title,body` で向き先と目的を読み、なければ向き先を main とする
   - 向き先との差分（`git diff origin/<向き先>...HEAD`）、コミット（`git log origin/<向き先>..HEAD`）、HEAD のコミット SHA を読む
   - 対象から外すファイルを決める。`git check-attr linguist-generated` が `true` の生成物と、バイナリファイル。外したファイルは結果に書く
   - 差分が規約の目安（1,000行）を超えていたら、レビューの精度が落ちうることを人に伝える
   - 根拠になる文書を集める。規約（`docs/conventions/`）、steering、差分やコミットに出てくる ADR、関係する spec（requirements.md、design.md、tasks.md）
4. 変更の種類を判定し、動かすサブエージェントを決める

   | 変更の種類 | 動かすサブエージェント |
   |---|---|
   | ドキュメントだけ（`.md` だけで、`.claude/skills/` を含まない） | 正しさとセキュリティを除く5つの観点に1つずつ |
   | それ以外（コード、skill、スクリプト、設定を含む） | すべての観点（7つ）に1つずつ |

   - skill は AI の動きを、スクリプトや設定はツールの動きを変えるので、拡張子が `.md` でも「それ以外」として扱う
   - 外から来る入力の検証、ファイル、外部プロセス、DB、認証に触る変更なら、「正しさ」と「セキュリティ」のサブエージェントに、その部分を重点として伝える
5. 決めたサブエージェントを、Agent ツールで1つのメッセージから並列に起動する。モデルは `sonnet` を指定し、`run_in_background: false` でフォアグラウンドで動かす。バックグラウンドで動かすと、`claude -p` のセッションが待ちきれずに途中で終わるため。1つのサブエージェントには `docs/conventions/review.md` の「観点」の表の1行だけを担当させる。全体の時間は最も遅いサブエージェントで決まるので、1つが見る範囲を狭くして待ち時間を短くし、観点ごとに集中して見落としを減らすため

   各サブエージェントに渡すもの
   - 向き先と比較範囲（`origin/<向き先>...HEAD`）、対象から外したファイル、PR の目的、根拠になる文書のパス、重点（あれば）
   - 担当する観点と、`docs/conventions/review.md` を読んでその規約に従うこと（指摘しない範囲を除く、確信がないものは出さない）
   - 読んで判断すること。挙動を確かめるためにコマンドを実行しない、ファイルを作らない、`claude` を起動しない。使ってよいのは、ファイルを読むことと、`git diff`・`git log`・`git show` だけ。読んで判断できないことは、確信がないものとして出さない
   - 件数の目安は伝えない。「指摘の数」の節のとおり、問題がなければ0件と返してよいこと、見つかった問題はすべて返すことをはっきり伝える
   - 返す形式: 指摘ごとに、観点、仮の優先度、場所（ファイル:行）、何が起きるか、なぜ問題か（根拠の文書の該当箇所を含む）、該当コードの引用、修正の方針と差分。引用は実物からそのまま写すこと
6. すべての指摘の妥当性を検証し、内容を確定する（ここはサブエージェントに任せない）
   1. 一覧にする: サブエージェントの結果を仮の優先度で並べる
   2. すべての指摘で確かめる。1つでも満たさなければ取り下げ、理由を記録する
      - 指摘した場所が実在し、引用が実物と一致する（サブエージェントの引用を信用せず、自分で読む）
      - 根拠にした規約・ADR・spec に、指摘のとおりのことが書いてある
      - 指摘しない範囲や、対象から外したファイルに入っていない
      - 上流（入力の検証、フレームワークの設定、呼び出し元）ですでに防いでいない
   3. Critical と High の候補は、さらに裏取りする。呼び出し元や関連するファイルまで読み、どの入力でどう壊れるかを具体的に説明できなければ降格する。確かめた箇所を「確かめたこと」として記録する
   4. 観点どうしの矛盾を調停する: たとえば「正しさ」は防御を足せと言い、「シンプルさ」は減らせと言う場合、要件と ADR に照らしてどちらを採るか決め、理由を記録する
   5. 重複をまとめ、優先度を確定する: 同じ箇所・同じ趣旨は1件にまとめ、検出元の観点を併記する。複数の観点が指摘したことは、優先度を上げる理由にしない。件数をそろえるために、指摘を足したり、まとめたり、削ったりしない
7. 結果を `.review/<ブランチ名>.md`（`/` は `-` に置き換える）に、次の形式で書き出す。同じファイルがあれば上書きする。差分は、自分で読んだ実物のコードに対して作る
8. 指摘の件数と、Critical・High の内容と、手順2で消したファイルを人に伝える

## 出力の形式

人が上から順に読んで、何が起きて、なぜ困って、どう直すかが分かるように書く。冗長にしないため、次を守る。

- 「何が起きるか」と「なぜ問題か」は、それぞれ2文まで
- 引用は10行まで。差分は変わる箇所だけで15行まで。収まらない修正は、手順を箇条書きにし、要所の差分だけを示す
- 「確かめたこと」は Critical と High にだけ書き、1文にする
- 見出しの下には一覧表だけを開いたまま置き、件数や要点をまとめた文は書かない。指摘の詳細、取り下げた指摘、対象は、すべて1つの閉じた状態の折りたたみ（`<details>`）にまとめる。人は一覧表で全体を見て、詳しく読みたいときだけ開く
- 指摘が0件のときは、一覧表の代わりに「指摘なし」とだけ書く。取り下げた指摘と対象は、同じく折りたたみに入れる
- 見出しの「レビュー」の後に番号は付けない。PR 本文で何回目のレビューかは `/pr` が付ける

````markdown
### レビュー（HEAD <コミット SHA の先頭7文字>、<YYYY-MM-DD HH:MM>）

| 番号 | 優先度 | 観点 | 要約 | 場所 |
|---|---|---|---|---|
| R-1 | <優先度> | <観点> | <一行の要約> | <ファイル>:<行> |

<details><summary>詳細（指摘 <n>件・取り下げ <m>件）</summary>

#### R-1 [<優先度>] <一行の要約>

**何が起きるか**：<どんな状況で、どんな結果になるか>

**なぜ問題か**：<どの要件・設計・規約に反し、どんな実害があるか>

**該当コード**（`<ファイル>:<行>`）
```<言語>
<該当箇所の引用>
```

**修正案**：<直し方の方針を1文で>
```diff
<変更前と変更後の差分>
```

**確かめたこと**：<Critical・High のとき、読んで確かめたファイルと箇所>

#### 取り下げた指摘

- <指摘の要約> — <取り下げた理由>

#### 対象

- ブランチ: <ブランチ名>（向き先: <向き先>）
- 変更の種類: <ドキュメントだけ / それ以外>（<動かした観点>）。対象から外したファイル: <ファイル、または「なし」>
</details>
````

指摘の番号（R-1、R-2…）は、人が「人の判断」で対応を書くときに使う。取り下げた指摘がなければ、その小見出しは書かない。0件はそのまま0件として書き、言い訳や補足の指摘を足さない。
